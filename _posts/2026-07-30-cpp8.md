## 一、第一段：顺序执行——最原始的“面向过程”

在没有任何抽象的情况下，程序就是**从上到下逐条执行的指令序列**。它完全按业务流程的时序逻辑来组织，即“先做什么，后做什么”。

```c
/* 一个简单的"上班"流程，纯顺序执行 */
int main(void) {
    /* 步骤1：起床 */
    int is_awake = 1;
    /* 步骤2：洗漱 */
    int is_clean = 1;
    /* 步骤3：吃早餐 */
    int is_full = 1;
    /* 步骤4：出门上班 */
    int is_at_work = 1;
    return 0;
}
```

**特点**：直接、直观，与人类按步骤做事的习惯一致。但**数据和操作完全分离**，每一步都暴露在主流程中，没有任何封装。

**局限性**：如果“上班”这个步骤需要修改（比如今天要先去取快递），或者需要在“起床”和“上班”之间加“洗漱”，所有写死这个顺序的地方都得手动调整。更糟糕的是，如果程序中多处重复了类似的顺序（例如工作日和周末的流程），每一处都要同步修改，极易遗漏。

## 二、第二段：独立函数调用——结构化编程的进步

为了解决顺序执行带来的维护难题，我们引入了**函数**，将具体的业务动作封装成独立的过程。主流程不再关注具体实现，只负责按顺序调用这些函数。

```c
void wake_up(void) {
    /* 起床的具体步骤（可能涉及闹钟、穿衣等） */
}

void wash(void) {
    /* 洗漱的具体步骤 */
}

void eat_breakfast(void) {
    /* 吃早餐的具体步骤 */
}

void go_to_work(void) {
    /* 上班的具体步骤 */
}

int main(void) {
    wake_up();
    wash();
    eat_breakfast();
    go_to_work();
    return 0;
}
```

**核心思想**：**模块化与复用**。每个功能被隔离成一个独立的函数，可以单独测试和修改。主程序（如 `main`）只关心流程控制——调用了哪些函数，而不关心函数内部的实现细节。

**特点体现**：
- **高内聚**：每个函数聚焦于单一职责，内部实现对外隐藏。
- **可维护性**：如果“吃早餐”的逻辑变了，只需修改 `eat_breakfast` 函数内部，所有调用它的地方无需改动。
- **可测试性**：可以独立验证每个函数的行为。

**进步性**：相比顺序执行，这无疑是巨大的飞跃。它避免了重复代码，降低了修改的扩散范围。然而，这仍然只是“过程式抽象”的第一步——它仍然面向操作，数据（如人的状态）需要在函数之间通过参数传递或通过全局变量共享，并未从根本上解决数据与操作的分离问题。

## 三、面向过程编程的深层缺点

尽管结构化编程改善了代码组织，但随着系统复杂度持续增长，以下问题依然突出：

### 3.1 数据与操作的分离仍然存在

函数是“操作”的载体，数据（结构体、数组等）是独立的实体。这种分离导致新增操作或新增数据类型时，代码修改依然会扩散。

例如，假设我们有一个 `Student` 结构体，并编写了 `calc_score`、`print_info` 等函数。如果后来要增加“计算平均绩点”的操作，则需要添加一个新函数；如果要增加一个 `Teacher` 类型，又必须为其重复实现类似的函数集。这种“横切”式的扩展，使得代码难以增量发展。

### 3.2 全局变量与隐式状态的滥用

由于函数间传递参数有时显得繁琐，许多程序员倾向于使用全局变量来共享数据。这导致：
- **隐式耦合**：函数可能不经意间修改全局状态，调用者难以预料。
- **测试困难**：必须精心设置全局环境的初始值，且测试间互相干扰。
- **认知负担**：阅读代码时，不得不时刻关注哪些全局变量被哪些函数修改。

### 3.3 并发环境下的脆弱性

多线程程序中，全局共享状态成为数据竞争和死锁的温床。函数之间的隐式交互使得并发推理极为困难，必须依赖繁琐的锁机制，增加了开发成本和出错概率。

### 3.4 复用层次依然不够灵活

虽然函数提供了基本的复用单元，但复用粒度往往过大（整个函数）或过小（单条语句）。缺乏像高阶函数或组合那样的灵活手段，导致大量重复代码，或者被迫通过拷贝粘贴来“复用”，维护成本居高不下。

## 四、函数式编程思想——另一种视角

函数式编程提供了一套不同于过程式的解决方案，其核心原则可以弥补上述缺点。

### 4.1 纯函数：消除副作用

**纯函数**是指对于相同输入，总是返回相同输出，且不修改任何外部状态（无副作用）。在C中，我们可以尽量将函数设计为只依赖参数、不访问全局变量、不进行I/O操作。

```c
/* 纯函数示例：只依赖参数，无副作用 */
int add(int a, int b) {
    return a + b;
}

/* 非纯函数：依赖并修改全局计数器 */
int global_counter;
void increment(void) {
    global_counter++;   /* 有副作用 */
}
```

纯函数易于测试、推理和缓存，且天然线程安全（无需加锁）。

### 4.2 不可变数据：避免共享状态

虽然C没有内置的不可变数据结构，但我们可以通过设计约定——例如，函数返回新副本而非原地修改——来模拟不可变性。这样，数据一旦创建就不会被更改，多个函数可以安全地共享同一数据而不担心冲突。

```c
struct Point {
    int x;
    int y;
};

/* 返回新的 Point，原 Point 不变 */
struct Point add_point(struct Point p1, struct Point p2) {
    struct Point result;
    result.x = p1.x + p2.x;
    result.y = p1.y + p2.y;
    return result;
}
```

### 4.3 高阶函数：提升复用能力

通过函数指针，我们可以将函数作为参数传递，实现行为参数化。这大大提高了代码的通用性和组合性。

```c
/* 对数组每个元素应用操作 */
void apply_to_all(int *arr, int n, void (*func)(int *)) {
    for (int i = 0; i < n; ++i) {
        func(&arr[i]);
    }
}

/* 具体操作 */
void double_value(int *p) { *p *= 2; }
void square_value(int *p) { *p = (*p) * (*p); }

/* 使用 */
int data[3] = {1, 2, 3};
apply_to_all(data, 3, double_value);
/* data 变为 {2, 4, 6} */
```

### 4.4 避免全局变量

尽可能将所有需要的状态通过参数传递，而不是隐式依赖全局变量。如果多个函数需要共享配置，可以封装在结构体中并显式传递。

## 五、在C中混合使用两种范式

C语言不是函数式语言，但我们可以吸收其精华，与过程式方法结合使用：

- **宏观架构**：依然采用面向过程的方式划分模块和主流程。
- **微观实现**：在模块内部，尽量编写纯函数，减少副作用，使用 `const` 保护只读数据。
- **数据管理**：优先使用参数传递而非全局变量，对于需要共享的数据，采用显式的上下文结构体。
- **并发策略**：尽量使用不可变数据，减少锁的依赖。

这种“过程式骨架 + 函数式内核”的风格，已被许多成熟项目验证为务实有效的实践。

*P.S.：作者习惯将使用过程式骨架 + 函数式内核的编成思想成为面对函数编程，但是实际上没有这种说法*
