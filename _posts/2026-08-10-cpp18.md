## 1. `const` 与 `constexpr`

### 1.1 C 语言中的 `const`：只读变量
在 ANSI C 中，`const` 修饰的变量本质上是一个**只读的变量**：
- 它占用内存空间，具有存储期。
- 它的值在运行时确定（除非初始化器是常量表达式，但 C 标准并不强制要求编译期求值）。
- 默认具有**外部链接**（全局 `const` 变量可在其他文件中用 `extern` 声明引用）。
- 不能用作数组大小（在 C89/90 中，即使 `const int n = 10; int arr[n];` 也不被允许；C99 允许 VLA，但那是运行时，并非真正的常量）。

```c
/* C 语言 */
const int MAX = 100;      // 只读变量，仍占用内存
int arr[MAX];             // C89 错误，C99 作为 VLA（变长数组）
extern const int MAX;     // 可在其他文件链接到该变量
```

### 1.2 C++ 中的 `const`：编译期常量（当条件满足时）
C++ 对 `const` 赋予了两层含义，具体取决于初始化器是否为编译期常量表达式：
- 若初始化器是常量表达式（如字面量、`constexpr` 变量、枚举常量等），则该 `const` 变量**被视为编译期常量**，可用于数组大小、模板参数等需要常量表达式的位置。
- 若初始化器在运行时才确定，则退化为**只读变量**（类似于 C）。

```cpp
// C++ 
const int MAX = 100;       // 编译期常量（初始化器是字面量）
int arr[MAX];              // 合法！编译期确定大小

int getValue() { return 42; }
const int DYNAMIC = getValue(); // 运行时初始化，不是常量表达式
// int arr2[DYNAMIC];     // 错误！DYNAMIC 不是编译期常量
```

**关键差异**：顶层 `const` 全局变量的链接性在 C++ 中默认是**内部链接**（仅本文件可见），与 C 相反。若需外部链接，必须显式加 `extern`：

```cpp
// C++ 中，默认内部链接
const int MAX = 100;        // 仅在当前 .cpp 可见
extern const int SHARED = 200; // 外部链接，可在其他文件用 extern 访问
```

### 1.3 `const` 成员函数
在类中，`const` 修饰成员函数表示该函数**不会修改对象的非 `mutable` 数据成员**，且可被 `const` 对象调用。
```cpp
class Point {
    int x, y;
public:
    int getX() const { return x; }          // 只读
    void setX(int val) { x = val; }         // 非常量
};
void foo(const Point& p) {
    int a = p.getX();   // 合法
    // p.setX(5);       // 错误：const 对象不能调用非常量成员
}
```

### 1.4 `constexpr`（C++11 起）——显式的编译期常量
`constexpr` 是 C++11 引入的关键字，用于**强制要求在编译期求值**。它可修饰变量、函数和构造函数。

- **`constexpr 变量`**：必须由常量表达式初始化，且值在编译期确定。
- **`constexpr 函数`**：函数返回值可以在编译期计算，但也可在运行时调用（若参数为常量表达式则编译期求值，否则退化为普通函数）。
- **`constexpr` 构造函数**：使类对象可以在编译期构造（用于模板元编程）。

```cpp
constexpr int square(int x) { return x * x; }

int main() {
    constexpr int N = 5;                 // 编译期常量
    constexpr int S = square(N);         // S 在编译期求值为 25
    int a = square(10);                  // 也可以在运行时调用（参数非常量表达式）
    return 0;
}
```

**`const` 与 `constexpr` 选择**：
- 若变量必须编译期已知（如数组大小、模板参数），用 `constexpr`。
- 若变量在运行时初始化但之后不再修改，用 `const`。
- 从 C++11 起，`constexpr` 是更精确的编译期常量声明工具。

## 2. 内联函数（`inline`）——替代宏

### 2.1 C 宏函数的缺陷

宏（`#define`）在预处理阶段进行纯文本替换，存在以下典型问题：

1. **参数多次求值**：`#define SQUARE(x) ((x)*(x))` 调用 `SQUARE(++i)` 会展开为 `((++i)*(++i))`，导致未定义行为。
2. **运算符优先级问题**：若忘记加括号，可能引发错误（如 `#define MUL(a,b) a*b` 调用 `MUL(1+2,3+4)` 展开为 `1+2*3+4`）。
3. **无法调试**：宏在预处理后消失，断点无法设置。
4. **类型不安全**：宏不进行类型检查。


### 2.1.1 宏滥用的典型场景

除了上述固有缺陷，宏在实际工程中还常被滥用，带来维护性、可读性和安全性上的隐患：

- **用宏定义“伪函数”实现复杂逻辑**  
  例如定义 `#define MAX(a, b) ((a) > (b) ? (a) : (b))`，虽然常见，但若参数带有副作用（如 `MAX(++x, y)`）则会展开为 `((++x) > (y) ? (++x) : (y))`，导致变量多次自增。即使改用 `inline` 模板函数即可完全避免此类问题。

- **宏定义多语句块缺少 `do { … } while(0)` 保护**  
  ```cpp
  #define LOG(msg) std::cout << msg; std::cerr << msg;   // 错误！
  if (debug) LOG("error");   // 展开后 if 只控制第一个语句，第二个无条件执行
  ```
  正确写法应使用 `do { … } while(0)`，但该写法依然无法调试，且破坏了代码结构。

- **宏作为“代码生成器”过度使用**  
  有些项目用宏批量生成类似函数或变量，导致错误定位困难、IDE 无法自动跳转，且宏展开后的错误信息晦涩难懂，极大降低调试效率。

- **宏污染全局命名空间**  
  宏没有作用域，即使在函数内部 `#define`，也会影响后续所有代码，且无法通过 `namespace` 隔离。常见于 `#define min max` 之类的重命名，意外替换标准库函数，引发隐蔽的编译错误。

- **用宏代替常量或枚举**  
  `#define PI 3.14` 不参与类型检查，且无法获得地址，调试时查看符号也不友好。现代 C++ 推荐使用 `constexpr` 或 `const` 常量。

**结论**：宏仅应谨慎用于条件编译（如 `#ifdef`）等预处理控制，**不应**用于表达可计算的逻辑或常量，这些场景应优先使用 `inline` 函数、模板或 `constexpr`。

### 2.2 `inline` 函数的语义

C++ 使用 `inline` 关键字向编译器**建议**将函数体在调用点展开，以消除函数调用开销（但编译器可忽略该建议）。与宏相比：

- 函数具有作用域和类型。
- 参数只求值一次，且遵循 C++ 的求值顺序。
- 支持重载、模板、调试信息。
- 有语法检查（类型、返回值）。

```cpp
inline int square(int x) {
    return x * x;
}
int main() {
    int i = 2;
    int a = square(++i);   // i 只增加一次，结果为 a=9, i=3
    return 0;
}
```

### 2.3 内联函数的链接性

- 在类定义内部定义的成员函数**默认是 `inline`**。
- 在类外部使用 `inline` 关键字定义的函数，若在头文件中定义且被多个 `.cpp` 包含，链接器会合并重复定义（不会造成多重定义错误）。
- **建议**：小型函数（1~5 行）定义在头文件中并标记 `inline`，大型函数由编译器自行决定是否内联（即使声明 `inline`，编译器也可能忽略）。

### 2.4 静态内联 与 普通内联

- C 语言中常用 `static inline` 在头文件中定义小函数，避免多重定义。
- C++ 中推荐使用 `inline`（不加 `static`），因为 `inline` 函数具有**外部链接**，但由于其“弱符号”特性，多个翻译单元中的定义会合并，不会冲突。

## 3. 匿名命名空间（Anonymous Namespace）与 `static` 全局变量

### 3.1 C 语言的文件作用域 `static`
在 C 中，在文件顶层（所有函数之外）使用 `static` 修饰全局变量或函数，表示其**链接性为内部（internal linkage）**，仅在本翻译单元（.c 文件）内可见，其他文件无法访问。这是实现文件内私有符号的标准方式。

```c
// file1.c
static int private_counter;   // 仅 file1.c 可见
static void helper() {}       // 仅 file1.c 可见
```

### 3.2 C++ 推荐使用匿名命名空间
C++ 保留了 `static` 的这种用法，但更推荐使用**匿名命名空间**，因为：
- **适用范围更广**：`static` 只能修饰函数、变量和某些类型（在 C++ 中也可以修饰类型，但语法别扭），而匿名命名空间可以**包裹任意声明**（类、结构体、枚举、模板特化等）。
- **语义更清晰**：匿名命名空间明确表达“本文件私有”的意图，且不会与函数内的 `static` 局部变量混淆。
- **与模板友好**：某些模板实例化需要在匿名命名空间内进行私有化。

**语法**：
```cpp
// file.cpp
namespace {
    // 私有符号
    int internal_counter;
    void helper_function() {}
    struct InternalType { int x; };
}
```
**重要事实**：匿名命名空间中的符号实际上具有**外部链接**（external linkage），但编译器为其生成一个**唯一的、不可见的名字**（如 `_ZN12_GLOBAL__N_1...`），从而在符号层面与其他翻译单元区分开。因此，匿名命名空间可以达到文件私有效果，且不违背链接规则（C++ 标准要求它等同于 `namespace unique { ... } using namespace unique;`）。

### 3.3 对比与建议
| 特性 | 文件作用域 `static` | 匿名命名空间 |
|------|---------------------|--------------|
| 适用对象 | 函数、变量（C++ 中也可用于类型，但不标准） | 任意声明（类、模板、枚举、函数、变量） |
| 链接性 | 内部链接 | 外部链接（但名字被编译器唯一化） |
| 对模板的影响 | 不支持包裹模板特化 | 支持 |
| 代码可读性 | 分散的 `static` 关键字 | 集中在一个 `namespace {}` 块中，分组清晰 |
| C++ 标准推荐 | 不推荐 | 推荐（作为文件内私有符号的标准方式） |

**客观结论**：在 C++ 中，优先使用匿名命名空间实现文件作用域的私有声明；仅在需要与 C 兼容或保持传统 C 风格时才使用 `static`。

## 综合示例

```cpp
// 将三个特性结合使用
#include <iostream>
using namespace std;

// 1. constexpr 编译期常量
constexpr int MAX_SIZE = 100;

// 2. inline 函数（替代宏）
inline int clamp(int val, int low, int high) {
    return (val < low) ? low : (val > high) ? high : val;
}

// 3. 匿名命名空间（替代 static）
namespace {
    // 私有类型与函数
    struct Helper {
        static int transform(int x) { return x * 2; }
    };
    int privateCounter = 0;
}

int main() {
    // 使用 constexpr
    int arr[MAX_SIZE];  // 编译期确定大小

    // 使用 inline 函数
    int v = clamp(5, 0, 3);   // v = 3

    // 访问私有符号（本文件内可见）
    privateCounter = Helper::transform(privateCounter);
    cout << privateCounter << endl;
    return 0;
}
```
