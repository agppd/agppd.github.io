## 1. 调试工具链：GDB 是基石

### 1.1 编译选项：调试信息的生成

调试的前提是编译时保留符号信息。GCC/Clang 使用 `-g` 选项生成调试信息（DWARF 格式）：

```bash
g++ -g -O0 -o program main.cpp
```

**关键权衡**：
- `-O0`（无优化）：变量完整保留在内存中，`print` 命令可靠，单步执行与源码行对应清晰。
- `-Og`（优化调试）：平衡优化与调试能力，适合性能敏感但仍需调试的场景。
- `-O2`/`-O3`（高度优化）：变量可能被优化到寄存器或完全消除，`print` 可能失效，此时需结合 `info registers` 和内存查看定位。

### 1.2 GDB 启动方式

```bash
gdb ./program              # 直接调试可执行文件
gdb --args ./program arg1 arg2  # 带参数启动
gdb -p <PID>               # 附加到运行中的进程
gdb ./program core         # 分析 core dump 文件
```

### 1.3 核心命令速查

| 类别 | 命令 | 作用 |
|------|------|------|
| **断点** | `break main` / `break file.cpp:42` | 设置断点 |
| | `break 10 if i==5` | 条件断点 |
| | `tbreak 20` | 临时断点（触发一次后自动删除） |
| | `info breakpoints` | 查看所有断点 |
| **执行** | `next` / `n` | 单步执行（不进入函数） |
| | `step` / `s` | 单步执行（进入函数） |
| | `continue` / `c` | 继续执行到下一个断点 |
| | `finish` | 执行完当前函数并返回 |
| **查看** | `print var` / `p var` | 打印变量值 |
| | `backtrace` / `bt` | 查看调用栈 |
| | `info locals` | 查看当前栈帧局部变量 |
| | `info args` | 查看当前栈帧参数 |
| **内存** | `x/40xw $esp` | 查看内存 |
| **寄存器** | `info registers` | 查看所有寄存器 |
| **反汇编** | `disassemble /m main` | 混合显示源码与汇编 |

## 2. 断点的底层原理：软件断点与硬件断点

断点是调试器最核心的功能。理解其原理有助于你在面对疑难问题时选择正确的断点类型。

### 2.1 软件断点（Software Breakpoint）

**原理**：调试器在目标指令处插入一条特殊的陷阱指令。

- **x86 平台**：插入 `int 3` 指令（机器码 `0xCC`）。
- 当 CPU 执行到 `int 3` 时，触发中断，操作系统将控制权转交给调试器。
- 调试器恢复原指令，等待用户继续执行。

**特点**：
- 数量不限（可设置任意多个断点）。
- 只能设置在**指令地址**上（代码段）。
- 修改了程序的内存（插入 `0xCC`），但调试器会妥善恢复。

### 2.2 硬件断点（Hardware Breakpoint）

**原理**：利用 CPU 内置的**调试寄存器**（x86 架构的 `dr0` ~ `dr7`）。

- `dr0` ~ `dr3`：存储要监控的内存地址。
- `dr7`：控制每个断点的触发条件（读/写/执行）和长度（1/2/4/8 字节）。

当 CPU 执行内存访问时，硬件会自动比较访问地址是否与调试寄存器匹配，若匹配则触发调试异常。

**特点**：
- 可监控**数据访问**（读/写），不仅限于指令执行。
- 数量有限（x86 最多 4 个硬件断点）。
- 零性能损耗（由硬件直接处理，无需插桩）。
- 需要操作系统支持（仅内核可访问调试寄存器）。

### 2.3 GDB 中的断点类型

| GDB 命令 | 类型 | 用途 |
|----------|------|------|
| `break` / `b` | 软件断点 | 代码行/函数入口中断 |
| `hbreak` | 硬件断点 | 代码执行断点（硬件实现） |
| `watch` | 观察点（优先硬件） | 变量值被修改时中断 |
| `rwatch` | 硬件读观察点 | 内存被读取时中断 |
| `awatch` | 硬件读写观察点 | 内存被读或写时中断 |

**watch 的实现策略**：GDB 优先尝试硬件 watchpoint（快速、精确到指令），若硬件资源不足则回退到软件实现（每步执行后检查变量值，较慢且报告在下一语句）。

### 2.4 硬件断点实战示例

```bash
# 假设要监控地址 0xffffd11c 处的 int 变量
(gdb) x/10x $esp+0x4          # 先找到变量地址
0xffffd11c: 0x0000000a ...

# 设置硬件读写观察点（必须指定类型和长度）
(gdb) awatch *(int*)0xffffd11c
Hardware access (read/write) watchpoint 3: *(int*)0xffffd11c

# 继续执行，命中时显示旧值和新值
(gdb) c
Continuing.
Hardware access (read/write) watchpoint 3: *(int*)0xffffd11c
Old value = 10
New value = 15

```

## 3. 进程内存布局：理解地址空间的“地图”

调试内存相关问题时（段错误、野指针、内存泄漏），必须先理解进程的虚拟内存布局。**每个地址都属于某个特定区域**，知道地址落在哪个区域，就能快速判断问题类型。

### 3.1 Linux x86-64 用户空间内存布局

```
低地址
  ┌─────────────────────┐
  │  .text (代码段)      │ ← 可执行指令，只读
  ├─────────────────────┤
  │  .rodata (只读数据段) │ ← 字符串常量、const 全局变量
  ├─────────────────────┤
  │  .data (已初始化数据) │ ← 已初始化的全局/静态变量
  ├─────────────────────┤
  │  .bss (未初始化数据)  │ ← 未初始化/零初始化的全局/静态变量
  ├─────────────────────┤
  │  堆 (Heap)           │ ← malloc/new 分配，向上增长
  ├─────────────────────┤
  │  共享库映射区         │ ← mmap 加载的 .so 文件
  ├─────────────────────┤
  │  栈 (Stack)          │ ← 局部变量、函数调用帧，向下增长
  ├─────────────────────┤
  │  vdso/vvar           │ ← 内核映射到用户空间的快速系统调用
高地址 
```

### 3.2 常见段错误与内存区域的对应关系

| 错误现象 | 可能原因 | 涉及区域 |
|----------|----------|----------|
| 访问 `0x00000000` | 空指针解引用 | 无效地址（未映射） |
| 访问 `0x41414141` | 使用未初始化的指针 | 无效地址 |
| 写入 `.text` 区域 | 通过野指针修改代码段 | 代码段（只读） |
| 写入 `.rodata` 区域 | 修改字符串常量 | 只读数据段 |
| 栈附近访问越界 | 栈溢出/缓冲区溢出 | 栈区域 |
| 堆附近访问越界 | 堆缓冲区溢出/use-after-free | 堆区域 |

### 3.3 GDB 中查看内存布局

```bash
# 查看进程的内存映射（在 GDB 中）
(gdb) info proc mappings
# 或从 shell 查看
cat /proc/<PID>/maps
```

## 4. 汇编级调试：读栈

当源码级调试不足以定位问题时（如栈被破坏、bt 输出全是 `??`），需要进入汇编层面分析。

### 4.1 x86-32 函数调用栈的经典结构

以 `main → func0 → func1` 的调用为例：

```cpp
int func1(int a) { int b = a + 1; return b; }
int func0(int a) { int b = func1(a); return b; }
int main() { int a = 1234; func0(a); return 0; }
```

**编译为 x86-32 汇编（关键片段）**：

```assembly
main:
    leal    4(%esp), %ecx
    andl    $-16, %esp
    pushl   -4(%ecx)
    pushl   %ebp              # 保存旧 ebp
    movl    %esp, %ebp        # 设置新栈帧
    pushl   %ecx
    subl    $20, %esp         # 分配 20 字节局部变量空间
    movl    $1234, -8(%ebp)   # 局部变量 a = 1234
    movl    -8(%ebp), %eax
    movl    %eax, (%esp)      # 参数压栈（通过 esp）
    call    func0             # 调用 func0
    ...
```

**call 指令做了两件事**：
1. 将**返回地址**（`call` 的下一条指令地址）压栈。
2. 跳转到目标函数。

**函数入口的标准序言（prologue）**：

```assembly
func0:
    pushl   %ebp              # 保存调用者的 ebp
    movl    %esp, %ebp        # 设置自己的 ebp
    subl    $20, %esp         # 分配局部变量空间
```

**栈帧布局**（从高地址到低地址）：

```
高地址
  ┌─────────────────┐
  │  参数 a          │ ← 8(%ebp)
  ├─────────────────┤
  │  返回地址         │ ← 4(%ebp)
  ├─────────────────┤
  │  调用者的 ebp    │ ← (%ebp)  ← 当前 ebp 指向这里
  ├─────────────────┤
  │  局部变量 b      │ ← -4(%ebp)
  ├─────────────────┤
  │   ...            │ ← -20(%ebp)  ← esp 指向这里
  └─────────────────┘
低地址

```

### 4.2 x86-64 的重要差异

x86-64 使用**寄存器传递参数**（前 6 个整数参数依次放入 `rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9`），而非全部压栈。这意味着：
- 查看参数时需检查寄存器而非栈内存。
- 栈帧结构更紧凑，但理解起来需要额外注意寄存器状态。

### 4.3 GDB 汇编调试常用命令

```bash
# 显示当前函数的汇编代码（混合源码）
(gdb) disassemble /m

# 单条汇编指令执行
(gdb) stepi    # 执行一条汇编指令（进入函数）
(gdb) nexti    # 执行一条汇编指令（不进入函数）

# 每次停顿时自动显示当前汇编指令
(gdb) display /i $pc

# 查看寄存器
(gdb) info registers
(gdb) info registers rbp rsp rip

# 查看栈内存
(gdb) x/20x $rsp

```

## 5. 性能分析与硬件事件：perf 与 VTune

调试不仅用于“找 bug”，还用于**找性能瓶颈**。这类调试需要借助 CPU 硬件性能计数器。

### 5.1 perf（Linux 内核自带）

`perf` 直接读取 CPU 的硬件性能计数器，可采样分析：

```bash
# 统计程序执行的 CPU 周期和指令数
perf stat ./program

# 采样分析热点函数（生成报告）
perf record -g ./program
perf report

# 生成火焰图（需配合脚本）
perf script | stackcollapse-perf.pl | flamegraph.pl > flame.svg
```

**可监控的硬件事件**：CPU 周期、指令数、缓存命中/未命中、分支预测失败、TLB 缺失等。

### 5.2 Intel VTune / AMD uProf

商业级性能分析工具，提供更细粒度的硬件事件分析：
- 微架构分析（流水线停顿、端口利用率）。
- 内存访问分析（NUMA、带宽）。
- 多线程并发分析。

## 6. 崩溃分析：Core Dump 与堆栈回溯

当程序在生产环境崩溃时，通常没有交互式调试器可用。此时 **core dump** 是唯一的“事故现场”。

### 6.1 启用 Core Dump

```bash
ulimit -c unlimited          # 允许生成 core 文件
# 运行程序，崩溃后生成 core 文件
./program
# 用 GDB 分析
gdb ./program core
```

### 6.2 Core Dump 分析流程

```bash
(gdb) bt              # 查看崩溃时的调用栈
(gdb) bt full         # 显示所有栈帧的局部变量
(gdb) frame 2         # 切换到第 2 帧
(gdb) info locals     # 查看该帧的局部变量
(gdb) list            # 显示对应源码
(gdb) disassemble     # 查看崩溃点的汇编
```

### 6.3 栈被破坏时的应对

如果 `bt` 输出全是 `??`，说明栈已被破坏。此时：
1. 检查 `rip`（指令指针）和 `rsp`（栈指针）的值。
2. 用 `x/` 命令手动查看栈内存，寻找残留的返回地址。
3. 结合汇编分析，推断崩溃前的执行路径。

## 7. 内存错误检测：Valgrind

Valgrind 的 Memcheck 工具通过**动态二进制插桩**监控所有内存操作：

```bash
valgrind --leak-check=full --show-leak-kinds=all ./program
```

**可检测的问题**：
- 内存泄漏（`malloc`/`new` 未配对 `free`/`delete`）。
- 无效读写（访问已释放或未分配的内存）。
- 越界访问（读写超出分配块边界）。
- 使用未初始化的值（配合 `--track-origins=yes`）。

**局限**：Valgrind 会显著降低程序运行速度（通常慢 10~50 倍），不适合在生产环境长期运行。

## 8. 多线程调试

GDB 默认调试多线程程序时，一旦中断，**所有线程暂停**。

| 命令 | 作用 |
|------|------|
| `info threads` | 查看所有线程 |
| `thread <ID>` | 切换到指定线程 |
| `set scheduler-locking on` | 调试当前线程时，其他线程暂停 |
| `set scheduler-locking off` | 调试当前线程时，其他线程继续执行 |
| `watch var thread 1` | 仅线程 1 修改 var 时触发观察点 |
